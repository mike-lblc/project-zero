0. Резюме и вердикт

P0 — не рой равноправных LLM-агентов, а детерминированный планировщик с 19 узкими ролями, общей базой SQLite и одним рассуждающим шагом на оборот. Интеллект намеренно разделён по трём ярусам: локальные модели (Ollama) делают механику и выбор одного инструмента из белого списка; всё, что является суждением, уходит в очередь эскалаций и решается фронтирной моделью в сессии владельца; облако (GitHub Actions) исполняет только сетевые и базовые шаги. Такая архитектура даёт высокую предсказуемость и слабую «глубину планирования»: ни один агент не строит многошаговый план, кроме нового дилера с явным циклом OBSERVE→MODEL→PRIORITIZE→ACT→VERIFY→LEARN.

Вердикт по стабильности: система устойчива к падениям процесса (сторож каждую минуту, часовой аудит, замок экземпляра), к повторам без прогресса (пауза с удвоением) и к чужим инструкциям (шлюз). Она не устойчива к трём вещам, найденным этим аудитом и частично исправленным в тот же день: самоухудшение кода улучшателем (дважды снимал предел чтения), клоны зонтичной задачи (9 копий за 5 дней) и расхождение двух реплик базы между облаком и машиной владельца. Системный промпт = MISSION (перевод денег от постороннего на кошелёк, проверяемый хешем) + COMMON (правила честности и доказательств) + текст роли (3,8–5,0 тыс. символов) + строка KPI + меню инструментов с сигнатурами + факты состояния в JSON + требование ответить одной строкой JSON {"tool","args","why"}. Побудительный шаблон один на всех: «выбери ОДНО действие, предпочитай новое знание или продвижение к деньгам, не повторяй сработавшее без изменения условий».

2.3 The Planning — модуль планирования

Паттерн — одношаговый ReAct без цепочки: наблюдение состояния → выбор ровно одного инструмента → исполнение → запись исхода в agent_decisions. Глубина рекурсии планирования = 1 на оборот; многошаговость возникает из очереди задач (core.execution): задача не создаётся без исполнимого следующего действия, провал обязан породить ровно одну следующую попытку (родитель уходит в REJECTED), завершение требует доказательства. Сделка проходит 16 состояний с регулярными выражениями доказательств для каждого перехода (CONTACTED — URL или id сообщения; PAID — хеш транзакции).

Исключения из одношаговости: (а) дилер — явный цикл OBSERVE→MODEL→PRIORITIZE→ACT→VERIFY→LEARN с формулой приоритета P(перевода)·P(подтверждения)·доступность ÷ ожидаемое время; (б) совет (DECISION_PROTOCOL): Proposer с обязательным фальсификатором → Verifier без доступа к рассуждению предлагающего (антиякорение) → Adversary с целью убить предложение → Judge, обязанный разобрать сильнейшее возражение; на RED действует асимметричное вето одного доказанного возражения. Совет исполняется фронтирной моделью; в базе 2 предложения, 5 возражений, 2 решения — структура есть, статистики исходов ещё нет.

Ограничители петель: один и тот же результат три раза подряд (SAME_LIMIT=3) → пауза 5·2ⁿ минут с потолком по шагу (наблюдение платежей 15 мин, свежие премии 20, PR 60, снабжение 180, максимум 24 ч); та же ошибка трижды — та же пауза.

3. Профиль автономности и самоэволюции

3.1 Self-Learning

  • Репутация ролей (agent_reputation, 91 строка): вызовы/верные по каждому шагу; наблюдается, но не меняет маршрутизацию автоматически.
  • Уроки по смыслу: recall.remember() пишет выводы в векторную память; при следующем решении агент получает до 3 близких уроков — это RAG с обратной связью, но односторонней: сходство не переоценивается по исходам.
  • Память цикла: система замечает собственное повторение и меняет поведение (пауза, next_focus).
  • Дилер: после каждой попытки обновляет модель контрагента (вероятность ответа, возражения, кооперация), доли успеха стратегий и оценку вероятности следующего платежа — единственный агент с явным LEARN.
  • Экономика: economics.survival() считает отдачу агентов по стоимости шагов (spans) и выручке; при нулевой выручке помечает режим выживания.
  • Каталог инвариантов растёт из инцидентов (121 проверок, список списанных RETIRED) — обучение системы, а не модели.

4. Топология коммуникации и синхронизация состояния

4.1 Паттерн взаимодействия

Централизованная звезда вокруг общей базы с одним планировщиком. Агенты не вызывают друг друга и не держат соединений; всё общение — записи в SQLite, которые читает следующий оборот. Внешние протоколы — HTTP/JSON (GitHub API через gh, Moltbook REST, Coinbase Bazaar, Blockscout/Blockstream/Hiro/Solana RPC, Cloudflare), никаких WebSocket или gRPC.

4.2 Синхронизация состояния и гонки

  • Один процесс-планировщик: замок data/worker.pid с проверкой живости PID; второй экземпляр не стартует. Сторож различает «процесс есть» и «журнал свежий» — живым считается тот, кто оставляет след моложе 300 с.
  • Конкурентная запись: WAL + busy_timeout 60 с + db.write() с шестью повторами и линейной задержкой; запись решения агента не имеет права уронить оборот (три повтора, затем потеря записи, но не работы).
  • Оптимистическая блокировка событий: UPDATE events SET claimed_by=? WHERE claimed_by IS NULL — двое не возьмут одно; событие, взятое и брошенное более 30 минут, возвращается в очередь (stale/release).
  • Идемпотентность внешних действий: квитанции Moltbook по хешу запроса (UNIQUE, провалившиеся переименовываются для повтора); поступления по хешу транзакции (UNIQUE — двойной учёт невозможен); задача с той же целью не создаётся второй раз; обращение одному адресату — один раз навсегда.
  • Две реплики базы: облачный прогон восстанавливает brain.db из артефакта и загружает обратно; локальная и облачная копии расходятся и не сливаются. Поэтому шаги, пишущие наружу под одной личностью (обращения дилера, сдача на AIBTC), исполняются только на машине владельца (CLOUD_CANNOT).
  • Документированная гонка: остановка пультом сначала снимает сторожей и кладёт KILL_SWITCH, и только потом убивает воркер — иначе сторож, запущенный секундой раньше, поднимал воркер после остановки.

5.2 Агент-отладчик — что есть и как устроен

Роль надзора разнесена по трём детерминированным контурам и одному агенту; языковая модель в контуре восстановления не участвует намеренно — перезапуск и откат должны срабатывать, когда модель как раз недоступна.

Принудительное прерывание зависших сессий. Шаги исполняются синхронно в одном процессе; прерывания «по агенту» нет. Зависание останавливается тремя способами: таймауты на всех сетевых вызовах и подпроцессах (HTTP 20–60 с, модель 300 с, аудит 600 с, git 180 с); пауза шага после трёх одинаковых результатов или ошибок; сторож, который через 5 минут без записей в журнал убивает процесс целиком и поднимает новый (состояние в базе, поэтому потеря — не больше одного шага).

5.3 Профиль отладчика, который стоит достроить

  1. Бюджет времени на шаг с жёстким прерыванием. Сегодня шаг может держать цикл на всю сумму своих таймаутов (наблюдался pursue около минуты, hunt_bounties 2 300 с за сутки). Вынести сетевые тяжёлые шаги в подпроцесс с общим лимитом (например 120 с) и учитывать превышение как сбой шага.
  2. Одна база вместо двух реплик. Облачный прогон читает и пишет собственную копию; события и эскалации, поднятые в облаке, не видит машина владельца. Минимум — облако только читает и публикует; лучше — общий удалённый SQLite (например, через Turso/libSQL, бесплатный тариф) с тем же WAL-подобным поведением.
  3. Ревью правок улучшателя адверсарием. Гейт стал строже, но смысл правки по-прежнему не оценивается. Добавить событие code_fix_applied с приоритетом 2 → adversary читает diff и таблицу code_fixes; при возражении — откат через существующий backup.
  4. Скоринг совета по исходам. Протокол требует взвешивать возражения и решения по тому, что случилось потом; данных 2 предложения / 5 возражений — дать судье обязательную обратную связь из состояний сделок.
  5. Метрика «время до обнаружения». KPI сторожа названо, но не измеряется: писать в audit_cycles разницу между первой записью о сбое и первым действием восстановления.
